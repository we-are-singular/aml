AML maintains its own [SDK and CLI changelogs](/docs/reference/changelog/) with the workflow in
[`scripts/changelog.aml.tsx`](https://github.com/we-are-singular/aml/blob/main/scripts/changelog.aml.tsx).

The workflow is two AML trees joined by one typed draft:

```text
<Agent read-write>
  gather authoritative commits and investigate them
  <FollowUp>return DraftSchema</FollowUp>
</Agent>
             ↓ structured draft
<Agent read-write>
  publish the draft
  <FollowUp>review, correct, and format</FollowUp>
</Agent>
```

<Aside type="tip" title="The tree performs the work">
  JavaScript does not inspect Git, parse versions, render Markdown, manipulate markers, or write files. The Agents run
  the repository-owned evidence command and inspect and edit the repository directly.
</Aside>

## Author from repository evidence

The first Agent has repository access and begins with the exact deterministic evidence command:

```tsx
const draft = await evaluate(
  <Agent provider={provider} permissions={{ filesystem: "read-write", network: false, shell: true }}>
    <System>
      You maintain AML's public changelog. Be factual, specific, and useful to readers. Never invent behavior, commits,
      versions, or documentation routes.
    </System>
    Author the next package changelog entry. Begin by running the supplied `release-notes.ts` command exactly as
    written, then inspect commits whose subjects do not explain their user impact.
    <FollowUp>
      Return the structured changelog draft with a title, overall summary, and reader-oriented highlights.
    </FollowUp>
  </Agent>,
  DraftSchema
)
```

The repository-owned script keeps commit selection deterministic. The Agent owns its invocation, investigation, and
editorial judgment. `<FollowUp />` keeps investigation and authoring in one provider-owned session, and its final
response is validated by `DraftSchema`.

## Keep one useful authoring schema

```tsx
const DraftSchema = z.object({
  title: z.string().trim().min(1),
  summary: z.string().trim().min(1),
  highlights: z
    .array(
      z.object({
        title: z.string().trim().min(1),
        details: z.string().trim().min(1),
        links: z.array(
          z.object({
            label: z.string().trim().min(1),
            href: z.string().trim().startsWith("/docs/"),
          })
        ),
      })
    )
    .min(1),
})
```

The schema defines the editorial handoff. It does not create a document parser or restrict Markdown inside the authored
fields.

## Publish and review in a second tree

The second Agent receives the structured draft and the exact target paths:

```tsx
return (
  <Agent provider={provider} permissions={{ filesystem: "read-write", network: false, shell: true }}>
    <System>
      Work only on the requested changelog. Preserve its frontmatter, introduction, existing entries, and newest-first
      ordering. Do not change package versions, tags, or other files.
    </System>
    Publish the supplied draft for the current package version.
    <FollowUp>
      Review the entry against the draft, package version, authoritative commits, existing style, and MDX syntax.
      Correct issues, run Oxfmt, and inspect the final diff.
    </FollowUp>
  </Agent>
)
```

It inserts the entry for the manifest's current version after the changelog's single insertion marker, formats the file,
reviews the result, and corrects issues before returning. Published entries remain ordinary MDX with visible version
headings rather than hidden per-release delimiters.

<Steps>

1. The Agent runs `release-notes.ts` to collect lane-specific commits from the latest matching tag.
2. The authoring Agent investigates the package and repository.
3. Its `<FollowUp />` returns `DraftSchema`.
4. The publication Agent writes the draft.
5. Its `<FollowUp />` reviews, corrects, and formats the result.

</Steps>

## Run before release

```sh
OPENCODE_API_KEY=... npm run changelog:sdk
OPENCODE_API_KEY=... npm run changelog:cli
```

These are the same commands used by the release hooks, so running one manually exercises the real workflow. Review or
discard the changelog diff afterward. During a release, changelog authoring runs immediately after release-it changes
the package version. A ten-minute deadline stops a stalled provider before release commit, tag, push, npm publication,
or GitHub release.
