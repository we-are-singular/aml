AML is easiest to learn by building a workflow with a clear job to do. This cookbook moves from a credential-free review pipeline to typed outputs, application [`<Tool />`](/docs/reference/primitives/tool/) capabilities, scoped [`<Mcp />`](/docs/reference/primitives/mcp/) access, filesystem resources, durable provider composition, and operational jobs.

Type reusable components with [`AML.Component<Props>`](/docs/ast/#type-application-components-explicitly). Import `AML` as a type from `@aml-jsx/sdk`; add `AML.PropsWithChildren<Props>` for optional nested content or `AML.PropsWithRequiredChildren<Props>` for required children.

<Aside type="tip" title="Recommended path">
  Start with [Build a code-review workflow](/docs/cookbook/code-review-workflow/). It demonstrates bounded filesystem
  evidence, a real Skill, typed specialist Agents, explicit parallelism, application validation, and synthesis without
  requiring model credentials by default.
</Aside>

## Before you begin

Start with [Getting started](/docs/getting-started/#1-create-a-project) for SDK installation, the JSX runtime configuration, and a runner. Recipes build on that setup and focus on AML component design: what belongs in the tree, what application code must validate, and who owns capabilities, resources, and results. Each recipe lists only its additional dependencies and environment requirements.

`@aml-jsx/sdk/testing` is an import path included in the SDK, not a separately installable package. Install `zod` for schema examples and `vitest` as a development dependency for test examples. A code block labeled “Complete source” is intended to run with its stated prerequisites; smaller blocks illustrate changes to that source or require the surrounding application's values.

Recipes show an application entrypoint that constructs and evaluates an `AmlRuntime`; some separate that entrypoint from a reusable workflow file. The maintained examples also support the shared repository runner. To run a workflow with the [experimental CLI](/docs/cli/) instead, export the AML tree, put required providers directly on their components, and use `npx aml run ./workflow.tsx`. Do not wrap a second `AmlRuntime` inside the exported CLI entry.

Each recipe opens with its goal and, where useful, badges that tell you what to prepare:

- <Badge text="No credentials needed" variant="success" /> runs without a model account. It may still use local files or
  Docker, as the prerequisites explain.
- <Badge text="Agent authentication required" variant="caution" /> needs a configured live Agent. Recipes that
  specifically require an API key say so.
- <Badge text="Docker required" variant="note" /> needs a running Docker daemon. Other resource badges name the required
  service or local files.

Comparison guides may have no badges. Check each recipe's prerequisites for the complete setup and its notes on file changes and isolation.

Recipe steps and claims are verified against the implementation and specification links in each page's API and
source links section.

## Control a session's authored turns

Use [deliberate editorial passes with FollowUp](/docs/cookbook/follow-up-editorial-passes/) when several authored instructions should run in one provider session. The recipe explains what AML guarantees, what conversation history remains provider-owned, and when separate evaluations are clearer.

## Recipe format

Each page follows the same reading order:

1. **Goal** — the user task and the AML shape it produces.
2. **Prerequisites** — credentials, executables, packages, and resource requirements.
3. **Complete source** — imports included, with provider assumptions visible.
4. **Run and expected output** — what is safe to execute and what success looks like, without repeating project setup.
5. **How it works** — why the components are composed this way, with links to the relevant component references, concepts, and provider or image contracts.
6. **Failure and security notes** — boundaries that should affect production decisions.
7. **API and source links** — public contracts and the maintained repository example.

For the repository's current runnable catalog, use the command on the [Examples](/docs/examples/) page. The runner remains the source of truth; the docs recommend paths by learning goal instead of maintaining a second export inventory.
